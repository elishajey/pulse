신규 인도

인도 사이버보안센터가 AI 감사 지침을 냈다 — 위험 4등급으로 감사 깊이가 갈리고 AI 사고는 6시간 안에 신고해야 한다

AI 시스템을 감사할 때 무엇을 어디까지 봐야 하는지를 국가 기관이 문서로 정했습니다. 인도 침해사고대응센터(CERT-In)가 2026년 11월 4일 「AI 보안 감사 지침」 v1.0을 발표했습니다[T1]. 뼈대는 등급제여서 AI 시스템을 Low·Moderate·High·Critical 네 등급으로 나눕니다. 등급은 고장 났을 때의 피해와 자율성·데이터 민감도·규모·필수 서비스 비중으로 정합니다[T2]. 상위 등급은 등록된 제3자 감사를 받아야 하고, Critical 등급에는 상시 모니터링까지 요구됩니다[T2].

운영 쪽 숫자도 함께 나왔습니다. 신고 대상 AI 보안 사고는 6시간 안에 알려야 하고 로그는 최소 180일 남겨야 합니다[T2]. 다만 이 수치는 언론 보도에 실린 내용입니다. 인도 리스크관리협회(RMAI)는 조항 단위로 대조할 전문을 확보하지 못했다고 적었습니다[T3].

국내 통신사도 이미 같은 축을 건드리고 있습니다. SK텔레콤은 올해 10월 사내 AI 에이전트 관리체계까지 ISO/IEC 42001 인증 범위를 넓혔습니다[T2]. KT는 자체 통제 기술을, LG유플러스는 외부 협력 기반 안전성 평가 체계를 키우고 있습니다[T2]. 금융보안원이 내놓은 AI 에이전트 평가 기준도 6개 영역 17개 점검항목으로 권한 통제와 사람 승인, 킬 스위치를 묻습니다[T2].

[elisha’s take] — AI 감사 기준이 권한·사람 승인·중단·로그 네 축으로 모이고 있습니다. 사내 에이전트 점검표를 그 네 축으로 다시 묶어 두십시오.

자세히 보기

등급이 감사 주기를 정한다 — 지침은 등급마다 감사 깊이와 주기를 다르게 둡니다[T2]. 자율성도 등급을 가르는 기준에 들어갔습니다. 사람 승인 없이 외부 시스템을 호출하는 에이전트는 같은 데이터를 쓰더라도 더 높은 등급으로 올라갑니다[T2]. 이는 NIST AI RMF의 Govern 기능이 요구하는 거버넌스 체계와 맞닿아 있습니다[T3].

같은 시기에 나온 공격 경보 — CERT-In은 AI 공격 도구를 쓰는 조직 Crafty Falcon이 인도 금융·보험 부문을 노린다고 경고했습니다[T2]. CSIRT-Fin 분석은 공개된 AI 공격 도구 네 가지를 지목했습니다. ARTEX, PentAGI, Cairn, CyberStrikeAI입니다[T2]. 공격자는 피해 기업의 결제·지급 API를 기계 속도로 호출했고, 지원 인프라는 몇 시간에서 며칠 단위로 IP를 바꿨습니다[T2]. 권고에는 주말·공휴일 인력 증원과 가상자산 출금 다중 서명이 들어갔습니다[T2].

국내 기준은 어디까지 왔나 — 국내에서는 금융 부문이 AI 감사·검증 기준을 먼저 숫자로 내놨습니다. 금융보안원 기준은 올해 말까지 시범 검증을 돌리고 정식 검사 기준은 2027년부터 적용할 예정입니다[T2]. 신고 시한만 보면 국내 제도는 AI 전용 시한을 따로 두지 않았습니다[T3].

[elisha’s take] — ① 사내 AI 시스템 목록에 자율성 항목을 추가합니다. 사람 승인 없이 외부를 호출하는 시스템부터 세어 둡니다. ② 에이전트 로그 보관 기간을 확인합니다. 180일은 인도 기준이지만 사고 조사에 필요한 하한으로 쓸 만합니다. ③ 해외 법인이 인도 금융권과 연동돼 있으면 결제·지급 API 호출량의 급증 탐지를 먼저 켭니다. ④ ISO/IEC 42001 인증 범위에 에이전트 관리체계가 들어가 있는지 증빙으로 확인합니다. 인증서만으로는 범위가 드러나지 않습니다.

중요도 높음 벤더 연구 공개

오픈AI 파이프라인이 30시간 만에 리눅스 커널 권한상승 익스플로잇 948개를 만들었다 — 1개당 비용은 1,279달러였다

오픈AI가 아직 공개하지 않은 사이버 모델로 리눅스 커널 결함을 찾고 익스플로잇까지 자동으로 만든 실험 결과를 내놨습니다[T1]. 10월 중순 실행에서 후보 2,308건을 찾아 30시간 안에 1,724건을 재현했고, 그중 948건이 동작하는 권한상승 익스플로잇이 됐습니다[T1]. 정보유출 취약점 291건의 PoC도 같은 실행에서 나왔습니다[T1]. 든 돈은 API 크레딧 1,213,430달러이고 익스플로잇 하나당 1,279달러입니다[T1]. 6월 GPT-5.5-Cyber가 권한상승 익스플로잇 24개를 찾았던 것에 비하면 40배에 가깝습니다[T2].

[elisha’s take] — 미패치 서버에서는 저권한 계정 하나가 곧 root입니다. 커널 패치가 밀린 서버부터 순서를 다시 잡으십시오.

자세히 보기

어떻게 돌렸나 — 파이프라인은 발견·동적 검증·악용 가능성 평가·패치 생성·사람 검토 다섯 단계입니다[T1]. 익스플로잇과 패치, 심각도 제안은 연구자가 검토한 뒤에 메인테이너로 넘어갑니다[T1]. 이 과정에서 새로 쓰인 커널 공략 기법도 열 가지입니다. 지속 탄성 객체 스프레이 2종, 페이지 그루밍 2종, 데이터 전용 5종, 임의 타입 혼동 1종입니다[T1].

패치는 아직 사람 손이 필요하다 — 오픈AI는 발견 속도에 패치 생성이 따라붙어야 한다고 적었습니다[T1]. AI가 만든 패치는 추가 지시와 반복, 전문가 지도를 거쳐야 쓸 만해졌습니다[T1]. VulnCheck는 AI를 활용한 취약점 발견을 위험이 커지는 영역으로 꼽았습니다[T2]. 실험 대상은 이름을 밝히지 않은 한 널리 쓰이는 리눅스 배포판이며, 커널 버전과 보호 기능 설정은 기사에 적히지 않았습니다[T3].

공개 건수는 이미 늘었다 — Google Threat Intelligence Group 집계로 월간 취약점 공개는 1월 5,045건에서 8월 10,740건으로 늘었습니다[T2]. 고위험 공개는 같은 기간 131건에서 350건이 됐습니다[T2]. 영국 NCSC도 AI 도구가 제로데이 발견을 거의 확실히 늘렸다고 봤습니다[T2].

[elisha’s take] — ① 리눅스 커널 패치 적용 지연일을 자산별로 뽑습니다. 권한상승은 내부 침입 뒤 단계라 외부 노출 여부로 우선순위를 가르면 놓칩니다. ② 공용 호스트에서 일반 사용자 계정을 쓰는 서비스를 찾아 계정 분리를 먼저 끝냅니다. ③ 컨테이너 호스트의 커널은 이미지와 따로 관리되니 패치 주기를 별도로 확인합니다. ④ 취약점 공개량이 두 배가 된 상황을 전제로 월간 패치 처리량의 상한을 다시 계산합니다.

중요도 높음 공급망 침해 · 노출 확인

ARTEX 복제판 도커 이미지에 백도어가 있었다 — 로그인 전에 root 명령이 돌고 그 상태로 열린 콘솔이 62대였다

지난 10월 28일과 11월 5일 호에서 공격 도구로 다룬 AI 공격 프레임워크 ARTEX가 이번에는 공격 경로로 등장했습니다[T2]. GitHub 복제판 trhhubsd/ARTEX는 docker-compose.yml 한 줄을 바꿔 정식 빌드 대신 tomicdd/artex 이미지를 받게 해 뒀습니다[T2]. 그 이미지의 로그인 처리에는 verifyCaptcha() 함수가 숨어 있습니다[T2]. CAPTCHA 입력이 정해진 표식으로 시작하면 나머지 문자열이 root 권한 sh -c로 실행되고 결과가 돌아옵니다[T2]. 자격증명 확인보다 먼저 돌기 때문에 인증 없이 root 쉘이 열립니다[T2]. 11월 2일부터 4일 사이 이 백도어 빌드를 띄운 콘솔 62대가 발견됐습니다[T2].

[elisha’s take] — ARTEX를 레드팀 도구로 받아 둔 조직이 가장 급합니다. 이미지 출처와 compose 파일을 지금 대조하십시오.

자세히 보기

얼마나 퍼졌나 — tomicdd/artex 이미지는 Docker Hub에서 다운로드 약 9,000회를 기록했습니다[T2]. 백도어 콘솔 62대의 위치는 미국 26대, 홍콩 17대, 중국 7대입니다[T2]. 11월 4일 기준 ARTEX 콘솔 전체는 1,645대였습니다[T2]. 첫 노출 사례는 이미지가 올라간 뒤 12일 지난 10월 20일에 나왔습니다[T2].

복제판이 하나가 아니다 — 원 개발자는 ARTEX가 실제 침입에 쓰인 뒤 GitHub 저장소를 내렸습니다[T2]. 그 뒤 복제본이 GitHub와 Docker Hub에 다시 올라왔습니다[T2]. trhhubsd/ARTEX는 스타 2,449개와 포크 600개를 넘겼습니다[T2]. congdonglinux/artex처럼 같은 백도어 이미지를 올린 다른 계정도 있습니다[T2].

저장소 코드만 읽으면 안 보인다 — 독립 연구자 Badbyte가 이미지를 분석해 숨은 함수를 찾았습니다[T2]. 악성 코드가 실행 파일이 아니라 컨테이너 이미지를 가리키는 한 줄 교체로 들어왔기 때문에, 저장소 소스만 검토하는 절차로는 드러나지 않습니다[T2]. 이 위험은 OWASP LLM Top 10의 공급망 취약점에 해당합니다[T3].

[elisha’s take] — ① 사내에서 받아 쓴 AI 보안 도구의 compose·Dockerfile에서 이미지 이름과 레지스트리 계정을 전부 뽑아 대조합니다. ② 이미지 다이제스트를 고정하지 않은 pull 설정을 찾아 해시 고정으로 바꿉니다. 태그만 믿으면 같은 사고가 반복됩니다. ③ ARTEX 콘솔을 띄운 적이 있으면 인터넷 노출 여부와 로그인 요청 본문에 표식 문자열이 있었는지 확인합니다. ④ 레드팀 도구는 별도 격리망에서만 돌리도록 승인 절차를 둡니다.

ChatGPT 잠금 모드가 팝업 하나로 풀렸다 — 클릭 없이 대화 내용이 빠져나갔다

Check Point Research가 ChatGPT의 Lockdown Mode를 우회하는 방법을 찾았고, 오픈AI는 9월 18일 이를 고쳤습니다[T2]. Lockdown Mode는 프롬프트 인젝션으로 데이터가 빠져나가는 범위를 줄이려고 오픈AI가 올해 6월 넣은 선택 설정입니다[T2]. 약점은 코드 블록의 HTML 미리보기가 팝업 창을 다루는 방식에 있었습니다[T2]. 미리보기는 중첩 샌드박스 프레임 안에서 돌고 새 창 열기도 막혀 있었지만, 샌드박스 권한 자체는 팝업을 허용했습니다[T2]. 프레임을 한 번 더 겹치면 손대지 않은 팝업 함수에 닿았고, 그렇게 열린 창은 샌드박스 제약을 벗어났습니다[T2].

[elisha’s take] — 잠금 모드를 켰다고 유출 대책을 끝내지 마십시오. 공유 대화와 외부 커스텀 GPT를 받는 경로부터 점검하십시오.

자세히 보기

어디까지 할 수 있었나 — 공격자는 조작한 프롬프트, 악성 커스텀 GPT, 공유된 대화로 이 경로를 열 수 있었습니다[T2]. 열린 창의 내용을 공격자가 정하므로 가짜 ChatGPT 업데이트 화면을 띄워 악성 파일을 받게 하는 수법도 가능했습니다[T2]. Check Point는 데스크톱 앱에서 클릭 없는 대화 유출이 성립한다고 적었습니다[T2]. 이는 OWASP LLM Top 10의 LLM01 프롬프트 인젝션에서 시작해 유출로 이어지는 경로입니다[T3].

데스크톱 앱만의 문제가 아니다 — 근본 약점은 Electron 기반 데스크톱 앱에만 한정되지 않습니다[T2]. CVE 번호와 심각도 점수는 공개되지 않았습니다[T3]. Check Point 연구 책임자 Eli Smadja가 결과를 설명했습니다[T2].

[elisha’s take] — ① 사내 ChatGPT 데스크톱 앱 버전을 9월 18일 수정 이후 버전으로 올렸는지 확인합니다. ② 외부에서 받은 커스텀 GPT와 공유 대화 링크는 업무 계정에서 열지 못하게 막습니다. ③ 업무용 LLM 계정에 연결된 커넥터 목록을 줄입니다. 유출 범위는 연결된 데이터 범위와 같습니다.

신규 한국

정부가 AI 에이전트용 제로트러스트 안내서를 냈다 — 도구 호출과 작업 위임마다 검증을 넣고 위험도에 따라 사람 승인을 받게 한다

AI 에이전트가 스스로 외부 도구를 부르는 환경에 맞춘 보안 기준이 정부 문서로 나왔습니다. 과학기술정보통신부와 한국인터넷진흥원이 2026년 11월 6일 「에이전틱 AI 제로트러스트 안내서」를 발간했습니다[T1]. 뼈대는 행동 단위 검증입니다. 입력 처리와 도구 호출, 작업 위임, 외부 통신마다 검증 절차와 보안 정책을 걸고, 위험 수준에 따라 사람 승인을 받게 했습니다[T2].

기준선은 지난해 12월 나온 「제로트러스트 가이드라인 2.0」의 4단계 성숙도 모델입니다. 안내서는 이 모델을 에이전틱 AI 환경으로 넓혀, 기업이 현재 수준을 자가 진단하고 개선 순서를 정하도록 했습니다[T2]. 법적 구속력은 없습니다. 고시가 아니라 권고 문서입니다[T1].

통신·플랫폼 업계는 이미 이 축으로 움직이고 있습니다. KT는 사용자와 단말의 신뢰도를 따져 접근을 허용하는 ZTNA를 이미 운영하고 있습니다[T2]. LG유플러스는 2027년까지 자사 환경에 맞춘 제로트러스트 모델을 목표로 단계별 로드맵을 세워 뒀습니다[T2]. 업계에서는 사람뿐 아니라 AI 에이전트까지 검증해야 하는 만큼 제로트러스트가 사실상 새 보안 표준이 되고 있다는 말이 나옵니다[T2].

[elisha’s take] — 사내 에이전트가 외부 도구를 부르는 지점을 먼저 목록으로 뽑으십시오. 안내서의 검증 지점이 그 목록에 그대로 붙습니다.

통제 대상이 넓어졌다 — 안내서는 보안 통제 범위를 사용자와 단말, 서버에서 외부 서비스와 물리 장치까지 넓혔습니다[T2]. 에이전트가 권한을 넘어 자율적으로 움직이거나 외부 입력을 받아 잘못된 명령을 수행하는 상황을 막으려는 목적입니다[T2]. 외부 입력이 에이전트 행동을 바꾸는 이 위험은 OWASP Top 10 for LLM Applications의 LLM01 프롬프트 인젝션과 같은 성격입니다[T3].

성숙도 모델을 그대로 쓴다 — 안내서는 새 등급 체계를 만들지 않고 「제로트러스트 가이드라인 2.0」의 4단계 성숙도 모델을 확장했습니다[T2]. 단계마다 실무 기준을 붙여, 기업이 지금 어디에 있고 무엇을 먼저 고칠지 정하게 했습니다[T2]. 도입 고려사항과 구축·운영 절차, 활용 예시도 함께 실렸습니다[T1]. 세부 통제 항목의 개수는 공개 자료에 적혀 있지 않습니다[T3].

고시와 안내서는 무게가 다르다 — AI 기본법 체계에서 기업에 직접 의무를 지우는 문서는 시행령과 고시입니다. 이번 안내서는 그 바깥의 기술 권고여서 위반에 따르는 제재가 없습니다[T1]. AI 기본법은 2026년 1월 22일 시행됐고 1년 이상 계도기간이 운영돼 그 기간에는 사실조사와 과태료 부과가 유예됩니다[T2]. 계도기간이 끝난 뒤 안전성 확보 의무를 어떻게 증빙할지 묻는 자리에서 이 안내서가 사실상 기준으로 쓰일 가능성이 있습니다[T3].

[elisha’s take] — ① 사내 에이전트가 호출하는 외부 도구와 API를 목록으로 만듭니다. 안내서의 네 검증 지점에 그 목록을 하나씩 맞춰 봅니다. ② 위험 수준별 승인 규칙을 글로 적습니다. 사람 승인이 필요한 행동과 사전 승인 정책으로 처리할 행동의 경계를 먼저 정합니다. ③ 「제로트러스트 가이드라인 2.0」 성숙도 자가진단을 이미 했으면 그 결과에 에이전트 항목을 덧붙입니다. 처음부터 다시 할 필요는 없습니다. ④ 에이전트가 쓰는 자격증명을 사람 계정과 분리합니다. 외부 통신 검증은 계정이 섞여 있으면 기록만 남고 통제가 되지 않습니다.

중요도 높음 연구팀 공개

브라우저 확장기능이 로그인 세션만으로 Claude Desktop에 명령을 넣었다 — 승인 창까지 스크립트가 눌렀다

claude.ai에 스크립트를 넣을 수 있는 브라우저 확장기능 하나로 사용자 PC에서 임의 코드가 실행됐습니다. Forever Security가 11월 6일 공개한 분석입니다[T1]. 원인은 Dispatch 기능이 일반 로그인 세션을 그대로 받아들이는 설계입니다. claude.ai 화면에는 연결 표시가 없는데도, 그 페이지에서 돌아가는 스크립트가 사용자인 척 Claude Desktop에 지시를 보낼 수 있었습니다[T1]. 시연에서는 프롬프트 네 개로 npm 패키지 설치를 요청했고, 모델이 낯선 패키지라며 망설였지만 사용자 계정으로 보낸 후속 메시지가 그 망설임을 풀었습니다[T1]. 승인 창이 공격자가 통제하는 웹페이지 안에 떠서, 스크립트가 1초마다 허용 버튼을 눌렀습니다[T1].

[elisha’s take] — 업무용 PC의 기기 간 Dispatch를 지금 끄십시오. claude.ai에 붙는 확장기능 목록도 함께 뽑아야 합니다.

자세히 보기

브라우저 취약점이 필요 없었다 — 시연은 전역 npm 설치까지 갔고, 패키지 설치 스크립트가 계산기 앱을 띄웠습니다[T1]. 연구팀은 같은 단계에서 파일을 빼내거나 백도어를 심을 수도 있었다고 적었습니다[T1]. Claude에 준 권한이 그대로 공격자 권한이 되는 구조입니다. MITRE ATLAS 전술로 보면 초기 접근 단계에 해당합니다[T3].

신고는 5월, 수정은 아직 — 연구팀은 2026년 5월 14일 Anthropic에 신고했습니다. Anthropic은 5월 19일 유효한 보고로 인정했지만 내부에서 이미 찾은 사안과 중복이라며 접수를 종결했습니다[T1]. 10월 13일에는 Dispatch를 10월 말을 목표로 종료한다고 연구팀에 알렸습니다[T1]. 지난주 갱신된 Dispatch 도움말에는 종료 안내가 없습니다[T2]. 신규 가입은 막혔고 일부 Pro·Max·Ultra 기존 사용자는 계속 쓸 수 있어, 악용 경로는 아직 열려 있습니다[T2].

같은 경로가 다른 기능에도 있다 — 연구팀은 Claude Code Remote Control과 Claude Cowork 세션에서도 같은 공격이 통한다고 봤습니다. 다만 두 기능은 시험하지 않았고 후속 글을 예고했습니다[T2]. 성립 조건은 세 가지입니다. claude.ai에서 스크립트를 돌릴 수 있는 확장기능, 두 곳에 모두 로그인한 상태, 켜져 있는 PC와 열린 데스크톱 앱입니다[T1].

실제 공격 사례는 보고되지 않았습니다[T1]. 다만 연구팀은 고객사 업무용 PC에서 기기 간 Dispatch가 켜진 개인 계정을 이미 발견했다고 적었습니다[T2].

[elisha’s take] — ① 업무용 PC에서 기기 간 Dispatch를 끕니다. 업무에 필요하면 기기 등록과 승인, 해제 절차를 글로 정해 두고 씁니다. ② claude.ai에서 스크립트를 돌릴 권한이 있는 브라우저 확장기능을 뽑습니다. 자동 업데이트로 권한이 늘어난 확장기능이 가장 위험합니다. ③ 확장기능 설치를 관리자 승인 목록으로 좁힙니다. 악성 확장기능이 아니라 정상 확장기능의 침해 업데이트가 경로였습니다. ④ 에이전트가 만든 패키지 설치와 설정 변경, 자격증명 접근, 외부 연결을 기록으로 남깁니다. 승인 창 클릭만으로는 추적이 되지 않습니다.

에이전트형 공격으로 Chainalysis 전체 사용자의 자격증명이 노출됐다 — Reactor와 KYT까지 중단했다

가상자산 추적 업체 Chainalysis가 전체 사용자의 이름과 사용자명, 비밀번호 해시, 유효 토큰이 공격자에게 노출됐다고 밝혔습니다[T1]. 10월 30일 첫 공지에서 이름과 이메일 같은 식별 정보에 그쳤던 범위가 조사 과정에서 전체 사용자로 넓어졌습니다[T2]. 회사는 공격자가 공격용 에이전트 기법으로 내부 시스템과 도구에 접근했다고 적었고, 뒤에는 통신을 가로채는 중간자 공격을 지목했습니다[T1]. 대응으로 로그인 포털과 Reactor, Data Solutions, KYT 인터페이스와 API, 주소 스크리닝을 중단했습니다[T1]. 조사용 그래프 데이터 접근이나 블록체인 귀속 데이터 조작의 증거는 없다고 밝혔습니다[T1].

[elisha’s take] — 이 도구를 쓰는 조직은 API 키를 먼저 교체하십시오. 같은 비밀번호를 쓴 다른 시스템도 함께 찾아야 합니다.

같은 달에 몰린 사건들 — Chainstack과 OpenCode, Warp, WorkOS도 AI를 쓴 공격을 알렸습니다[T2]. 마이크로소프트는 공격자가 공개 GitHub 저장소에서 노출된 비밀정보를 찾는 에이전트 프레임워크를 8월부터 쓰고 있다고 분석했습니다[T2]. 한 사례에서는 GitHub 비밀정보 탐색에서 Azure Key Vault 데이터 유출까지 5분이 걸렸습니다[T2]. 수집한 비밀정보로 서비스 주체 계정에 로그인해 Azure와 Microsoft 365 테넌트를 돌아다녔습니다[T2].

[elisha’s take] — ① 가상자산 컴플라이언스 도구의 API 키가 어디에 들어가 있는지 찾아 전부 교체합니다. 배치 작업과 사내 대시보드에 박힌 키가 가장 늦게 발견됩니다. ② 그 서비스 비밀번호를 다른 시스템에서 재사용했는지 확인합니다. 해시가 나갔으니 재사용 계정은 모두 교체 대상입니다. ③ 중간자 공격을 전제로 해당 서비스로 나가는 트래픽의 인증서 검증 설정을 점검합니다. 검증을 끈 연동 스크립트가 남아 있는지 함께 봅니다. ④ 서비스 주체와 앱 등록 계정의 로그인 기록을 뽑아 익숙하지 않은 IP를 찾습니다. 같은 수법이 다른 공급업체에서도 보고됐습니다.

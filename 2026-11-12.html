뉴욕주가 프런티어 AI 등록 창구를 열었다 — 1월 1일까지 등록하고 중대 안전사고는 72시간 안에 신고해야 한다

뉴욕주에서 가장 큰 AI 모델을 만드는 회사는 이제 주 정부에 이름을 올려야 합니다. 금융서비스부(DFS) 산하 DIGIT 사무소가 11월 10일 RAISE 포털을 열었고, 대형 프런티어 개발사의 등록 기한은 2027년 1월 1일입니다[T1]. 보안 담당자는 사고 신고와 모델 가중치 보호 조항을 먼저 봐야 합니다. 1월부터 대형 프런티어 개발사는 안전 프레임워크를 자사 웹사이트에 공개해야 하고, 프런티어 개발사 전체는 중대 안전사고를 신고하고 모델 투명성 보고서를 내야 합니다[T1]. 뉴욕주는 72시간 신고 기한을 전국에서 가장 엄격한 기준이라고 밝혔습니다[T1].

지난 11월 1일 호에서 다룬 RAISE법 확정과 2027년 1월 1일 시행 소식이 이번에 등록 창구 개설로 넘어갔습니다. 조문이 바뀐 것이 아니라 집행 기구가 실제로 가동된 단계입니다[T1].

국내 기업 대부분은 등록 의무자가 아니라 공급사를 관리해야 하는 위치에 있습니다. 업계 가이드는 배포자와 API 고객에게 공급사의 공개 프레임워크와 투명성 보고서를 받아 자체 제3자 AI 위험관리 절차에 연결하라고 권고했습니다[T2]. 금융권에는 AI 공급 계약에 72시간 사고 통지와 감사 권한, 협조 의무를 넣으라고 짚었습니다[T2]. 통신사와 플랫폼사가 해외 프런티어 모델을 얹어 서비스를 파는 구조라면, 공급사가 뉴욕주에 신고한 사고를 고객사에 언제 알리는지를 계약서에서 먼저 확인해야 합니다[T3].

[elisha’s take] — 해외 프런티어 모델을 쓰고 있으면 공급사의 RAISE 등록 여부와 사고 통지 조항을 이번 주에 확인하십시오.

자세히 보기

등록 의무자를 가르는 기준 — 대형 프런티어 개발사는 전년도 총매출 5억 달러를 넘고 10의 26제곱 연산 이상으로 학습한 모델을 가진 개발사를 말합니다[T2]. 계열사 매출을 합산해 따집니다[T2]. 남의 모델을 배포하거나 미세조정만 하는 회사는 등록 대상이 아닙니다[T2]. 등록 내용은 최신 상태로 유지해야 하고, 2년마다 또는 모델 소유권 이전이나 신고 정보의 중대한 변경 때 갱신합니다[T2]. DFS 보도자료 자체에는 매출과 연산량 기준이 적혀 있지 않습니다[T1].

중대 안전사고의 정의가 아직 비어 있다 — 72시간 신고 기한은 여러 자료에서 모두 같습니다[T2]. 다만 탈옥이나 모델 가중치 유출이 중대 안전사고에 들어가는지는 정리되지 않았다는 지적이 나옵니다[T3]. 과징금은 1차 위반 최대 100만 달러, 이후 위반 최대 300만 달러입니다[T2]. 미공개 모델 가중치를 어떻게 보호하는지 설명할 의무도 2027년 1월 1일부터 함께 적용됩니다[T2]. 안전 프레임워크 공개와 사고 신고를 함께 보면 NIST AI RMF의 Govern 기능이 요구하는 거버넌스 문서화와 맞닿는 성격의 의무입니다[T3].

같은 날 연구기관도 함께 세웠다 — 뉴욕주는 빙엄턴대학에 뉴욕 AI 책임성·연구센터(NYCAIRR)를 세웠습니다[T1]. 연구자 80명 이상이 모이고, 임시 공동소장은 Greg Morrisett과 Jeannette Wing입니다[T1]. DFS 대행 감독관 Kaitlin Asrow는 DFS가 DIGIT 사무소로 RAISE법 집행을 이끈다고 밝혔습니다[T1].

[elisha’s take] — ① 쓰고 있는 해외 프런티어 모델 공급사를 적어 두고 각각 RAISE 등록 대상인지 확인합니다. 매출 5억 달러와 연산량 기준이 갈림길입니다. ② 공급 계약에 공급사의 중대 안전사고 통지 조항이 있는지 봅니다. 뉴욕주에는 72시간 안에 신고하면서 고객사에는 알리지 않는 공백이 생길 수 있습니다. ③ 1월에 공개될 안전 프레임워크와 투명성 보고서를 받아 둘 창구를 정합니다. 제3자 위험평가 증빙으로 그대로 씁니다. ④ 가중치 보호 설명 의무가 적용되는 만큼, 공급사의 모델 가중치 접근 통제 수준을 질문지에 추가합니다. ⑤ 중대 안전사고 정의가 확정되면 계약 문구를 다시 맞춥니다. 지금은 범위가 열려 있습니다.

중요도 높음 KEV 등재 · 벤더 공지

GPU 클러스터 관리도구가 비밀번호 없이 관리자로 열렸다 — 리버스 프록시 뒤에 두면 바깥 요청도 로컬로 보인다

CISA가 GPUStack 인증 우회 결함 CVE-2026-102895를 11월 9일 악용된 취약점 목록에 올리고 연방기관 조치 기한을 11월 12일로 못 박았습니다[T1]. CVSS는 9.8이고, 벤더는 2.1.1 배포본을 노린 실제 악용을 확인했습니다[T2]. 원인은 자격증명이 없는 요청의 출처가 127.0.0.1로 보이면 내장 관리자로 처리하는 코드이고, 기본값이 그 상태였습니다[T2]. 같은 호스트에서 리버스 프록시로 받는 구성이면 외부 요청이 모두 로컬로 보여 누구나 관리자가 됩니다[T2]. 공격자는 관리자 API 키를 새로 만들고 추론 백엔드를 등록해 워커 호스트에 리버스 셸을 띄웠습니다[T2].

[elisha’s take] — GPUStack을 쓰면 오늘 2.2.2 이상으로 올리고, 올린 뒤에도 남아 있는 관리자 API 키와 추론 백엔드를 직접 지우십시오.

자세히 보기

로컬 판정이 두 갈래로 뚫렸다 — gpustack/api/auth.py의 get_current_user는 force_auth_localhost가 false일 때 요청 출처만 보고 내장 관리자로 처리했습니다[T2]. 호출자와 메서드, 경로는 확인하지 않았습니다[T2]. 내장 게이트웨이 모드에서는 클라이언트가 보낸 X-GPUStack-Real-IP 헤더를 그대로 믿어, 값을 위조하면 같은 분기로 들어갔습니다[T2]. 영향 범위는 2.1.1 이하이고, 2.2.0에서 로컬 우회 경로가 빠졌습니다[T2].

버전을 올려도 지워지지 않는 것 — 관리자 권한을 잡은 뒤 사용자와 모델, 설정을 바꾸고 워커와 클라우드 자격증명을 읽을 수 있었습니다[T2]. 스코프가 전체인 영구 관리자 API 키를 만들고, POST /v2/inference-backends/from-yaml 호출로 리버스 셸을 돌리는 백엔드를 등록했습니다[T2]. 공격자가 이미 만든 키와 백엔드는 업그레이드로 사라지지 않습니다[T2]. 관리자 계정과 API 키, 추론 백엔드, 워커 호스트를 점검하고 워커와 클라우드 자격증명을 교체해야 합니다[T2].

함께 고쳐야 하는 두 번째 결함 — 2.2.2는 SAML 콜백 우회 CVE-2026-102894도 막습니다[T2]. 이 결함은 0.7.1부터 2.2.1까지 영향을 받습니다[T2]. 노출된 인스턴스 수는 공개되지 않았고, Docker Hub 다운로드 94만여 건은 실제 운영 대수가 아닙니다[T2]. MITRE ATLAS 전술로는 초기 접근 단계에 해당합니다[T3].

[elisha’s take] — ① GPUStack 버전을 지금 확인하고 2.2.2 이상으로 올린 뒤 컨테이너를 다시 만듭니다. 2.2.0은 로컬 우회만, 2.2.2는 SAML 우회까지 막습니다. ② 당장 못 올리면 force_auth_localhost를 true로 바꿉니다. 리버스 프록시 구성에서 유일한 우회책입니다. ③ 프록시와 게이트웨이에서 클라이언트가 보낸 X-GPUStack-Real-IP 헤더를 제거합니다. 위조 헤더가 두 번째 경로였습니다. ④ 관리자 계정과 API 키 목록을 열어 모르는 항목을 폐기합니다. 스코프가 전체인 키가 남아 있으면 패치가 무의미합니다. ⑤ 추론 백엔드 정의를 하나씩 읽어 등록되지 않은 항목을 지우고, 워커 호스트의 외부 접속 기록을 되짚습니다.

중요도 중간~높음 연구팀 공개 보고서

잠자던 뉴런 7개만 고쳐 쓰면 에이전트가 시한폭탄이 된다 — 평가는 그대로 통과한다

마이크로소프트 연구팀이 11월 10일 재학습 없이 LLM에 백도어를 심는 Lazarus 기법을 공개했습니다[T2]. 마지막 피드포워드 층에서 쓰이지 않던 뉴런 몇 개의 가중치만 고쳐, 특정 문자열이 맥락에 들어오면 공격자가 정한 명령을 출력하게 만듭니다[T2]. Nemotron-Terminal-8B에서는 뉴런 1만2천여 개 중 7개를 고쳤습니다. 트리거가 있는 시험 23건에서 98.8% 이상 같은 명령이 나왔고, 트리거가 없을 때는 한 번도 작동하지 않았습니다[T2]. 마이크로소프트 위협 인텔리전스는 실제 공격자가 이 기법을 쓴 사례는 확인하지 못했다고 밝혔습니다[T2].

[elisha’s take] — 외부에서 받은 가중치 파일을 쓰고 있으면 공개된 기준 모델과 파일 해시를 대조하는 절차를 배포 전 단계에 넣으십시오.

자세히 보기

트리거는 평범한 문자열이면 된다 — 연구팀이 든 예는 날짜고, 시계가 2027년으로 넘어가는 순간 에이전트가 외부 코드를 받아 실행하는 명령을 내놓습니다[T2]. 맥락 어디에 들어오든 평범한 문자열도 트리거가 됩니다[T2]. 도구나 터미널 권한을 쥔 에이전트에서 위험이 가장 큽니다[T2]. Qwen 3.6-27B와 Gemma-4-31B-IT에서도 설정에 따라 51%에서 99.5%까지 성공했습니다[T2]. 연구팀은 2026년 2월 Claude Code와 Opus 4.5가 이 기법을 스스로 찾아냈다고 설명했습니다[T2].

탐지는 원본 가중치가 있어야 믿을 수 있다 — 에이전트가 만든 탐지 기법은 변형된 체크포인트의 91.4%를 잡아냈고 오탐은 9.7%였습니다[T2]. 원본 모델을 참조하지 않은 조건이었습니다[T2]. 연구 책임자 Dimitris Papailiopoulos는 어떤 검사도 모델이 안전하다고 증명하지는 못하며, 원본과 가중치를 대조해야 믿을 수 있다고 말했습니다[T2]. OWASP Top 10 for LLM Applications 기준으로는 공급망 항목에 가까운 위험입니다[T3].

권고된 통제 — 마이크로소프트 위협 인텔리전스는 배포 전과 갱신 후마다 가중치를 감사하고 체크포인트를 선언된 기준 모델과 대조하라고 권고했습니다[T2]. 배포자와 파일 해시를 검증하고, 출처를 확인할 수 없는 모델은 받지 말라고 했습니다[T2]. 승인된 모델은 접근을 통제하는 사설 레지스트리에 두라고 덧붙였습니다[T2]. 피해를 줄이는 쪽으로는 에이전트 권한 축소와 생성 코드의 격리 실행, 외부 통신 제한, 고위험 행동의 사람 승인을 들었습니다[T2]. 마이크로소프트는 Foundry에서 모델 출처를 검증하고 가중치 검사와 모델 서명 기능을 개발하고 있다고 밝혔습니다[T2].

[elisha’s take] — ① 사내에 올린 공개 가중치 모델 목록을 만들고 각각 어디서 받았는지 적습니다. 출처를 모르는 체크포인트부터 걸러냅니다. ② 배포 전 단계에 선언된 기준 모델과 파일 해시 대조를 넣습니다. 원본 없는 검사는 8.6%를 놓쳤습니다. ③ 터미널과 도구 권한을 가진 에이전트의 권한을 다시 깎습니다. 같은 백도어라도 권한이 없으면 명령이 돌지 않습니다. ④ 에이전트가 만든 코드는 격리 환경에서 돌리고 외부 접속을 허용 목록으로 제한합니다. ⑤ 모델을 받아 쓰는 외주와 계열사에 출처 확인 절차를 같이 적용합니다. 가장 약한 고리가 통로가 됩니다.

아직 공개되지 않은 것 — 서비스 이름과 그 서비스가 업로드 이미지를 어떻게 저장하고 처리하는지는 밝히지 않았습니다[T2]. 사진이 실제로 지워졌는지도 확인되지 않았습니다[T2]. 확산이나 악용 같은 2차 피해는 확인되지 않았다고 했습니다[T2]. 적용된 신고 조항과 기한도 공개 자료에서 드러나지 않았습니다[T3].

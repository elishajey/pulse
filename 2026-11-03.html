변동 확인 EU

AI법의 첫 조화표준이 관보에 실렸다 — 적합성이 추정되는 범위는 품질경영 하나뿐이고 보안 조항은 빠졌다

EU 집행위원회가 EN 18286:2026을 AI법의 첫 조화표준으로 인용했습니다[T1]. 시행결정 (EU) 2026/2274으로 2026년 10월 14일 관보에 실렸고, 부속서에 올라간 표준은 이 한 건뿐입니다[T1]. 보안 담당자는 먼저 이 표준을 따랐을 때 적합성이 추정되는 범위를 봐야 합니다. 범위는 AI법 제17조 품질경영체계뿐입니다[T1]. 정확성·견고성·사이버보안을 요구하는 제15조에는 아직 인용된 조화표준이 없습니다[T2]. 위험관리·데이터 거버넌스·로깅·투명성·인적 감독 조항도 아직 비어 있습니다[T2].

그래서 지금 고위험 AI의 보안 요구를 맞추는 방법은 두 가지입니다. 표준 없이 자체 근거로 제15조를 입증하거나, 사이버복원력법의 필수요구사항을 충족해 제15조 적합으로 인정받는 방법입니다. 다만 후자는 학술 분석의 해석일 뿐 집행위가 공식 확인한 내용은 아닙니다[T3]. CEN-CENELEC JTC 21은 사이버보안과 적합성평가를 포함한 나머지 표준 작업을 계속하고 있다고 밝혔습니다[T1].

EU에 고위험 AI를 수출하는 국내 기업이라면 이번 인용으로 덜어지는 일은 품질경영 문서뿐입니다. 보안 요구는 여전히 표준 없이 각자 증빙을 만들어야 하고, 통신·플랫폼 사업자가 쓰는 ISO/IEC 42001 인증서도 제17조 적합성 추정을 대신하지 못합니다[T2].

[elisha’s take] — 조화표준이 하나 생겼다고 고위험 AI 보안 증빙이 가벼워지지는 않았습니다. 제15조 증빙을 무엇으로 채울지 지금 정해 두십시오.

자세히 보기

조화표준 인용이 왜 중요한가 — AI법은 조화표준을 따른 시스템에 적합성을 추정해 줍니다. 추정이 인정되는 조항은 제3자 심사 없이 자체 선언으로 끝낼 수 있습니다[T2]. 추정이 없는 조항은 사업자가 요구를 충족했다는 근거를 스스로 모아 기술문서에 적어야 합니다[T2]. 이번 결정으로 이 길이 열린 조항은 제17조 품질경영체계 하나뿐입니다[T1].

출처마다 해석이 갈리는 부분 — 한 해설은 EN 18286의 문서화된 컴플라이언스 전략이 AI법 제9조부터 제15조까지의 필수요구사항을 다룬다고 설명했습니다[T3]. 이는 전략 문서에 담을 내용을 말한 것이지, 그 조항들에 적합성 추정이 붙는다는 뜻은 아닙니다[T2]. 두 해석을 섞으면 제15조 보안 증빙을 이미 갖춘 것으로 착각하게 됩니다.

ISO/IEC 42001과의 관계 — EN ISO/IEC 42001:2026은 CEN이 원문 수정 없이 유럽표준으로 승인했고 회원 34개국은 2026년 9월까지 이를 국가표준으로 채택해야 했습니다[T2]. 그러나 관보에 인용된 AI법 조화표준은 EN 18286:2026이고 42001은 아닙니다[T1]. 둘은 함께 쓰는 문서이지 서로를 대체하지 않습니다[T3].

[elisha’s take] — ① EU 고위험 AI 기술문서에서 제15조에 해당하는 항목을 따로 뽑아 각각 어떤 근거로 채웠는지 점검합니다. 비어 있으면 조화표준이 나올 때까지 자체 시험 기록이 그 자리를 메워야 합니다. ② 적대적 입력 내성과 모델 견고성을 재는 시험을 사내 배포 점검표에 넣습니다. 제15조가 요구하는 항목이라 나중에 표준이 나와도 그대로 쓰입니다. ③ 사이버복원력법 경로를 쓸지 법무와 미리 정리합니다. 공식 확인되지 않은 해석이라 이것만 근거로 삼으면 위험합니다. ④ ISO/IEC 42001 인증을 제17조 증빙으로 적어 둔 문서가 있으면 EN 18286 기준으로 다시 맞춥니다.

중요도 중간~높음 연구자 공개 · 벤더 패치 완료

파일 이름 끝 점 하나로 GitHub Copilot 쓰기 차단 우회 — 바뀐 설정 파일로 임의 명령 실행

Visual Studio와 SQL Server Management Studio(SSMS)의 GitHub Copilot에서 설정 파일 쓰기 차단을 우회하는 취약점이 공개됐습니다[T2]. CVE-2026-103572이고 CVSS 8.8, 마이크로소프트 등급은 Important입니다[T2]. Windows는 파일 이름 끝의 점을 무시합니다. 그래서 에이전트가 settings.json.에 쓰면 차단 검사는 이를 다른 파일로 보고 막지 않지만, 실제로는 settings.json이 바뀝니다[T2]. 연구자는 간접 프롬프트 인젝션으로 에이전트를 조종해 .mcp.json에 악성 MCP 서버를 등록했습니다. Visual Studio에서는 ripgrep 실행파일 경로를 바꿔, 다음 검색 때 원하는 프로그램이 실행되게 했습니다[T2]. 마이크로소프트는 10월 13일 경로를 정규화하도록 패치했고, 실제 악용은 보고되지 않았습니다[T2].

[elisha’s take] — 결함이 공유 DLL에 있어 Visual Studio 2022와 SSMS가 모두 영향을 받습니다. IDE만 업데이트하면 DB 운영 단말은 그대로 남습니다.

자세히 보기

차단 검사는 왜 뚫렸나 — Copilot은 설정 파일과 MCP 서버 정의 파일을 보호 대상으로 두고 쓰기를 막습니다[T2]. 그런데 이 검사는 경로를 정규화하지 않고 문자열로만 비교했고, Windows 파일 시스템은 끝의 점을 무시하고 같은 파일을 엽니다[T2]. 결함은 공유 구성요소인 Microsoft.VisualStudio.Copilot.Core.dll에 있었습니다[T2]. 패치는 GetFullPath 호출을 추가해 경로를 정규화하고 끝의 점을 제거합니다[T2].

설정 파일이 실행 경로가 되는 구조 — 두 공격 모두 별도의 코드 실행 취약점은 쓰지 않았습니다. 에이전트가 읽고 그대로 실행하는 설정 파일을 고쳤을 뿐입니다[T2]. MCP 서버를 등록하면 IDE가 공격자의 명령을 서버로 실행하고, ripgrep 경로를 바꾸면 사용자가 검색할 때 공격자의 프로그램이 실행됩니다[T2]. 연구자는 계산기 실행으로 시연했지만, 그 자리에는 어떤 명령이든 넣을 수 있습니다[T3].

지난 호와 무엇이 다른가 — 10월 31일 호에서 다룬 건은 Copilot CLI의 내장 브라우저가 작업 폴더 밖 파일을 읽은 문제였습니다[T2]. 이번에는 읽기가 아니라 쓰기이고, 대상도 CLI가 아니라 Visual Studio와 SSMS의 공유 구성요소입니다[T2]. 취약점 명칭도 출처마다 다릅니다. MSRC 권고는 Visual Studio 도구와 SSMS의 원격 코드 실행으로, 릴리스 노트는 SQL 도구 MCP 서버 문제로 표기했습니다[T2].

[elisha’s take] — ① 사내 Visual Studio와 SSMS가 10월 13일 이후 빌드인지 자산 목록에서 확인합니다. 공유 DLL이라 버전이 섞여 있을 수 있습니다. ② 개발 단말의 .mcp.json과 settings.VisualStudio.json 변경 이력을 파일 감사 대상에 넣습니다. 이 파일이 바뀌면 사람이 직접 확인해야 합니다. ③ 에이전트가 읽어 실행하는 설정 파일 목록을 따로 만듭니다. 쓰기 차단 우회는 이 목록의 모든 파일에 똑같이 통합니다. ④ 끝의 점이나 대소문자, 유니코드 치환으로 경로 비교를 속일 수 있는지 사내 도구에서도 확인합니다. Windows만의 문제가 아닙니다.

중요도 높음 복수 벤더 조사 · 실제 악성코드 배포 확인

에이전트 확장기능 마켓이 악성코드 유포 창구로 — 4,310개 중 44개가 한 캠페인과 연관, 다운로드 1만 2천 회 넘어

Lakera가 OpenClaw 확장기능 4,310개를 조사해 그중 221개를 정밀 분석했습니다[T2]. 44개가 ClawHavoc 악성코드 캠페인과 연관됐고, 다운로드는 1만 2,559회를 넘었습니다[T2]. Lakera는 실제 악성코드 유포가 확인된 점을 가장 심각한 발견으로 꼽았습니다[T2]. 피해를 키우는 건 권한 구조입니다. 확장기능은 사용자 로컬 권한으로 실행되고 환경변수를 읽을 수 있어, 설치되는 즉시 자격증명을 빼낼 수 있습니다[T2]. 다른 조사 결과도 같습니다. Koi Security는 2,857개 중 341개를 악성으로 분류했고, 그중 AMOS 스틸러를 유포한 335개는 같은 명령제어 서버 IP 하나를 썼습니다[T2].

[elisha’s take] — 확장기능은 사용자 권한으로 실행되고 환경변수를 읽습니다. 개발 단말의 API 키를 환경변수에 두고 있다면, 그 키가 바로 이번 공격이 노리는 대상입니다.

자세히 보기

수치가 출처마다 다른 이유 — 조사 시점과 대상이 다르기 때문입니다. Lakera는 4,310개, Koi Security는 2,857개를 조사했습니다. Koi Security는 이후 1만 700여 개로 늘어난 등록 목록에서 악성 확장기능을 824개 이상으로 다시 집계했습니다[T2]. Bitdefender는 검토한 확장기능의 약 17%에서 악성 의도를 확인했다고 밝혔습니다[T2]. 조사 대상이 서로 달라 수치를 합산하지 않았습니다[T3].

기존 검사로 왜 못 잡나 — 한 학술 정리는 바이너리 서명 위주의 검사 체계는 평문이나 평범한 셸 명령처럼 보이는 payload를 정상으로 판정한다고 지적했습니다[T2]. 확장기능은 바이너리가 아니라 지시문과 스크립트로 동작하기 때문에 기존 탐지 방식과 맞지 않습니다[T3]. 명령을 난독화하고 외부 붙여넣기(paste) 사이트를 거쳐 지갑·자격증명 탈취 악성코드를 내려받게 하는 수법도 보고됐습니다[T2].

위험 분류상 어디에 해당하나 — OWASP의 에이전틱 애플리케이션 위험 분류는 도구 호출과 위임된 권한을 자율 에이전트 고유 위험으로 두고 있습니다[T2]. 이번 사례는 모델을 속이는 공격이 아니라 에이전트 확장기능 공급망을 노린 공격이라, 모델 가드레일을 강화해도 막을 수 없습니다[T3].

[elisha’s take] — ① 사내에서 쓰는 에이전트 확장기능 목록을 뽑아 출처와 설치 시점을 적어 둡니다. 목록이 없으면 사고 때 무엇을 회수할지 정할 수 없습니다. ② 개발 단말의 API 키를 환경변수에서 빼고 단기 토큰을 발급받는 방식으로 바꿉니다. 이번 공격이 가장 먼저 노리는 것이 환경변수입니다. ③ 확장기능 설치를 사전 심사한 목록으로만 허용합니다. 마켓 전체를 열어 두면 사전 심사로 막을 것을 사후 탐지로 막아야 합니다. ④ 이미 설치된 확장기능의 외부 통신을 목적지별로 점검합니다. 여러 악성 확장기능이 명령제어 주소를 공유한 사례가 있어, 목적지 하나만 막아도 여러 건을 잡을 수 있습니다.

중요도 중간~높음 국내 매체 분석 · 당국 기준 준비 중

10월 연쇄 침해 뒤 국내 금융사 555곳 중 130곳이 보안 미흡으로 집계됐다 — AI 에이전트 점검 기준은 2027년부터다

10월 잇따른 금융권 침해 이후 국내 매체가 사후 집계를 내놨습니다. 금융사 555곳 가운데 130곳이 보안 미흡으로 분류됐습니다[T2]. 보도에 따르면 침해를 입은 곳은 빗썸·대신증권·미래에셋입니다[T2]. 당국은 이미 AI 에이전트 대응에 나섰습니다. 금융보안원이 AI 에이전트 보안 평가 기준안을 만들어 6개 분야 17개 점검 항목을 AI 레드티밍에 적용하기로 했고, 정식 점검 기준 도입은 2027년입니다[T2]. 공격 도구도 에이전트 구조로 바뀌고 있습니다. 금융권 침해에 쓰인 침투 도구 아르텍스는 계획을 세우는 플래너와 작업을 실행하는 워커로 나뉘고, 딥시크 같은 외부 모델을 연동했습니다[T2].

[elisha’s take] — 정식 기준이 2027년부터라는 건 올해와 내년 점검은 각사 자체 기준으로 한다는 뜻입니다. 금융보안원 17개 항목을 지금 자체 점검표에 넣어 두면 나중에 드는 비용이 줄어듭니다.

미흡 130곳이라는 숫자를 어떻게 읽나 — 이 집계는 침해 사실이 아니라 보안 수준 평가 결과입니다[T2]. 보도에 판정 기준과 평가 주체가 나와 있지 않아, 어떤 항목에서 미흡 판정이 나왔는지는 확인하지 못했습니다[T3]. 130곳을 침해 위험이 확정된 곳으로 읽으면 안 됩니다.

변동 확인 미국

학습데이터를 공개하라는 의무가 항소법원 법정에 올랐다 — 제9연방항소법원이 11월 18일 변론을 열었다

모델을 어떤 데이터로 학습했는지 공개하라는 캘리포니아법이 위헌 심사를 받습니다[T1]. 제9연방항소법원은 11월 18일 오전 9시 30분 패서디나 제1법정에서 xAI가 캘리포니아 법무장관을 상대로 낸 항소(사건번호 26-1591)의 변론을 열었습니다[T1]. 판결은 올해 안에 나올 예정입니다[T2].

보안 조직은 공개 항목부터 봐야 합니다. AB 2013(생성형 AI 학습데이터 투명성법)은 2026년 1월 1일부터 시행 중입니다[T2]. 공개 항목은 학습 데이터의 출처와 대략적 규모입니다. 저작권·라이선스 자료와 개인정보·합성데이터를 썼는지도 함께 밝혀야 합니다[T2]. 2022년 1월 1일 이후 출시하거나 상당히 수정한 시스템이 대상이라 소급 범위가 넓습니다[T2].

적용 기준은 회사가 어디 있느냐가 아니라 캘리포니아 주민에게 생성형 AI를 제공하느냐입니다. 그래서 국내 사업자도 같은 공개 의무를 집니다[T2]. Goodwin과 Crowell은 영업비밀을 비켜 갈 예외 조항이 없고 공개 서식도 정해지지 않았다고 지적했습니다[T2].

[elisha’s take] — 판결이 어느 쪽으로 나든 학습데이터 출처 대장은 만들어 둬야 합니다. 2022년치까지 거슬러 복원하는 일은 뒤로 밀수록 비싸집니다.

자세히 보기

소송 경과 — xAI는 2025년 12월 29일 캘리포니아 중부연방지방법원에 소를 냈고, 2026년 1월 16일 가처분을 신청했습니다[T1]. 법원은 3월 4일 신청을 기각했습니다. 쟁점은 심사 기준이었습니다. xAI는 상업적 표시 의무에 느슨한 Zauderer 기준을 적용하라고 주장했지만, 법원은 더 엄격한 Central Hudson 중간심사를 적용해도 법이 통과한다고 판단했습니다[T2]. xAI는 3월 17일 항소했고(제9연방항소법원 26-1591), 지방법원은 3월 23일 항소심이 끝날 때까지 집행을 정지했습니다[T1]. 주 정부 답변서는 7월 15일, 의견서(amicus)는 7월 21일과 22일, xAI 반박서는 9월 4일에 제출됐습니다[T1].

무엇을 다투는가 — xAI는 두 갈래로 공격합니다. 하나는 연방헌법 수정 제1조의 강제 표현(compelled speech) 법리이고, 다른 하나는 수용조항(Takings Clause)입니다[T2]. 주 정부는 변론에서 학습데이터 요약이 논쟁적 의견 표명이 아니라 영양성분표에 가깝다고 맞섰습니다[T2]. 캘리포니아는 7월 서면에서도 공개 요구가 대중에게 투명성을 준다는 중요한 정부 이익을 달성한다고 적었습니다[T2].

공개 의무가 보안 업무로 넘어오는 지점 — 이 법에는 준수 절차나 서식이 없습니다[T2]. 그래서 실제 작업은 데이터 출처 대장을 만드는 일로 수렴합니다. 어떤 코퍼스를 어디서 받아 어느 라이선스로 썼는지, 개인정보와 합성데이터가 섞였는지를 모델 판본별로 끊어 기록해야 합니다. 이는 AI 공급망 문서화와 같은 작업이고, ISO/IEC 42001이 요구하는 데이터 거버넌스 기록과도 겹칩니다[T2]. 사적 소송 조항은 없지만 책임 노출은 남아 있다는 분석이 있습니다[T2].

[elisha’s take] — ① 캘리포니아 이용자에게 열려 있는 생성형 기능을 먼저 셉니다. 무료 체험판과 API 재판매 경로가 빠지기 쉽습니다. ② 모델 판본별 학습 코퍼스 목록을 만들고 라이선스 근거 문서를 같은 줄에 붙입니다. 출처를 못 적는 코퍼스는 그 자체가 위험 항목입니다. ③ 영업비밀 예외가 없으니 공개문에 넣을 수준과 사내에만 둘 수준을 미리 갈라 둡니다. 법무가 아니라 데이터 관리자가 1차 분류를 해야 합니다. ④ 판결이 뒤집히면 집행 정지가 풀립니다. 공개문 초안을 지금 써 두고 판결 뒤 공개까지 걸리는 시간을 재 둡니다.

근거: CAIDP 사건 페이지(변론 공고) · Institute for Law & AI 분석 · 조문: AB 2013 전문 · 해설: Goodwin · Crowell

변동 확인 EU

나체 합성 앱 금지가 2주 뒤 적용된다 — 막을 장치가 없으면 범용 생성 모델도 금지 대상이 된다

12월 2일부터 EU에서 금지됩니다. Digital Omnibus(Regulation (EU) 2026/1744)가 AI법 제5조 금지목록에 두 항목을 넣었습니다. 식별 가능한 사람의 신체나 성적 행위를 동의 없이 사실적으로 생성하거나 조작하는 시스템, 그리고 아동 성착취물을 생성하는 시스템입니다[T2].

보안 관점에서 갈림길은 의도가 아니라 안전장치입니다. 공급자 금지는 두 경우에 적용됩니다. 첫째는 그런 생성을 시스템의 의도된 목적으로 삼은 경우입니다. 둘째는 설계·학습·구조·기능상 그런 결과가 합리적으로 예견되고 재현되는데도, 이를 확실히 막을 적절한 기술적 안전조치가 없는 경우입니다[T2]. 이용 사업자는 그 목적으로 썼을 때만 적용받아 범위가 좁습니다[T2].

이미 시장에 나와 있는 시스템에도 경과 예외가 없습니다[T2]. 지난 13일 호에서 다룬 제50조 투명성 지침(C/2026/6005)은 이 두 금지를 다루지 않아 해석 공백이 남습니다[T2]. 과징금 상한은 3,500만 유로 또는 전 세계 연매출 7% 가운데 큰 금액입니다[T2].

[elisha’s take] — 범용 이미지 생성 기능을 EU에 열어 둔 서비스라면, 안전장치가 있다는 말이 아니라 차단 기록이 증빙이 됩니다.

자세히 보기

조문 위치와 적용 시점 — 금지는 Art.5(1)(l) 계열로 들어가고 적용일은 2026년 12월 2일입니다[T2]. 과징금 근거는 Art.99(1)이며 상한은 3,500만 유로 또는 전 세계 연매출 7% 가운데 큰 금액입니다[T2]. 같은 개정으로 부속서 III 고위험 의무는 2027년 12월 2일, 부속서 I 제품 내장형은 2028년 8월 2일로 밀렸는데, 금지목록만 먼저 적용됩니다[T2].

안전조치가 면죄부가 되는 범위 — 두 단계를 섞어 읽으면 안 됩니다. 애초에 그런 생성을 목적으로 설계한 시스템은 분류기를 붙이거나 연령 확인을 걸어도 금지에서 빠져나오지 못합니다[T2]. 안전조치는 범용 생성 모델에서만 의미가 있습니다. 실인물 판별과 성적 콘텐츠 판별을 추론 시점에 걸어 둘이 함께 잡히면 생성을 끊고, 그 판단을 요청 ID와 시각, 판별 결과, 차단 사유로 남기라는 권고가 나와 있습니다[T2]. 다만 분류기 정확도 기준이나 검증 방법은 아직 제시되지 않았습니다[T3].

실제 사용 추이도 판단에 들어간다 — 공급자는 자기 시스템의 지배적 실사용이 그쪽으로 쏠리는지 지켜봐야 합니다. 쏠리면 금지 범위로 들어올 수 있습니다[T2]. 전문적 용례로 동의 기반 생성을 제공한다면 동의 기록을 암호학적으로 서명해 보관하고 시장감시당국이 요구할 때 제출할 수 있어야 합니다. 동의를 철회하면 생성물이 실제로 삭제되는 경로도 있어야 합니다[T2].

[elisha’s take] — ① 사내 서비스 가운데 이미지·영상 생성 기능을 EU 이용자에게 열어 둔 것을 골라 금지·위험·해당없음 세 칸으로 나눕니다. ② 실인물 판별과 성적 콘텐츠 판별을 추론 단계에 걸고, 차단 로그를 보존 기간과 함께 설계합니다. 로그가 없으면 안전조치를 증명할 방법이 없습니다. ③ 탈옥 시험을 품질 항목에서 컴플라이언스 항목으로 옮깁니다. 재현 가능 여부가 금지 판단의 문언이라 시험 결과 자체가 증빙입니다. ④ 이용약관과 API 허용사용정책, 재판매 계약에 해당 금지 조항을 함께 넣습니다. 공급자 금지와 이용자 금지가 따로 걸리므로 계약으로 책임선을 그어 둡니다.

AI 보안 · 서비스 동향 3선

중요도 높음 CISA 권고 · 과기정통부 공지

AI가 한 시간에 찾은 Java 결함에 CISA와 과기정통부가 잇따라 패치 공지를 냈다 — 국내 공공 정보시스템 72%가 Java다

Java 실행환경 안쪽에서 인증 없는 원격 코드 실행이 열렸습니다. OpenJDK의 Base64 디코더에 있는 메모리 손상 결함(CVE-2026-114938)입니다[T2]. 보안기업 Calif가 11월 17일 공개하며 Java4Shell이라고 이름 붙였습니다[T2]. 등급은 엇갈립니다. Oracle은 공격 난도가 높다며 CVSS 3.1 기준 8.1을 줬고, 보고자인 Calif는 CVSS 4.0 기준 9.2로 매겼습니다[T2].

이번 사건에서는 속도가 두드러집니다. Calif 연구원 한 명이 결함을 찾는 데 한 시간, 작동하는 익스플로잇을 만드는 데 두 시간을 더 썼고 토큰 비용은 200달러에 못 미쳤습니다[T2]. Jira와 Jenkins, Keycloak, Confluence에서 코드 실행을 재현했다고 밝혔습니다[T2].

대응은 하루 사이에 국내로 넘어왔습니다. Oracle이 11월 17일 정기 패치로 수정판을 냈고 같은 날 CISA가 즉시 패치를 권고했으며, 과기정통부와 KISA는 공공기관과 민간기업에 긴급 업데이트를 당부했습니다[T2]. 국내 노출 폭이 유독 넓습니다. JetBrains 2021년 조사에서 한국의 Java 사용률은 53%로 세계 평균 30%를 크게 웃돌았고, 정부 조사에서 공공 정보시스템의 언어 비중은 72%였습니다[T2].

[elisha’s take] — 자산 목록을 JDK 배포판과 판번호까지 끊어 두지 않은 조직은, 패치 대상을 세는 일부터 며칠을 씁니다.

자세히 보기

어디까지 영향을 받는가 — 영향 범위는 OpenJDK 17.0.6 이상입니다[T2]. Amazon Corretto와 Eclipse Temurin, Azul Zulu, Oracle Java SE 등 주요 배포판이 모두 들어갑니다. Microsoft Build of OpenJDK도 포함됩니다[T2]. 수정 판번호는 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1입니다[T2]. 표준 Java 8과 11은 대체로 비켜 가지만 Oracle Java SE 8 Enterprise Performance Pack은 영향을 받습니다[T2].

모든 환경에서 터지지는 않는다 — VulnCheck 연구팀은 취약한 코드 경로가 AVX-512 VBMI와 BW 명령어를 지원하는 CPU에서만 돈다고 밝혔습니다[T2]. Calif도 조직이 Base64를 어디에 쓰는지에 따라 달라져 보편적 익스플로잇은 없다고 적었습니다[T2]. 11월 17일 기준으로 Qualys와 Upwind는 실제 악용 사례를 확인하지 못했고 CISA KEV 목록에도 올라 있지 않습니다[T2]. 그래도 즉시 조치 등급으로 분류했습니다. CISA 권고와 국내 당국 공지가 이미 나왔고 인증 없이 터지는 경로이기 때문입니다.

Base64가 왜 문제인가 — Base64 디코딩은 입구에 있습니다. JWT 복호, 쿠키와 헤더 파싱, 멀티파트 업로드, 직렬화 데이터 처리처럼 인증 전에 도는 경로에서 쓰입니다. 그래서 공격면이 로그인 뒤가 아니라 로그인 앞에 놓입니다. 이번 결함은 라이브러리가 아니라 런타임 자체에 있어 성격이 다릅니다. 애플리케이션 의존성 목록을 뒤져도 안 나오고, 호스트의 JDK 판번호를 봐야 합니다[T2].

같은 흐름의 두 번째 사례 — Calif는 한 달 전인 10월 21일 PHP에서 같은 방식으로 찾은 결함(PHP2Shell)을 공개했습니다[T2]. 지난 17일 호에서는 구글 위협인텔리전스그룹이 패치 비교로 공격코드를 만드는 자동화를 공격 측에서 확인한 사례를 다뤘습니다. 이번 건에서는 같은 속도가 방어 측 연구에서도 나왔습니다.

[elisha’s take] — ① 호스트 단위로 JDK 배포판과 판번호를 뽑습니다. 애플리케이션 의존성 스캔으로는 런타임 결함이 안 잡힙니다. ② 인증 전 Base64 디코딩이 도는 경로를 먼저 골라 패치 순서를 정합니다. 외부 공개 API 게이트웨이와 SSO 끝단이 앞순위입니다. ③ AVX-512 지원 CPU 여부로 우선순위를 나눌 수는 있지만 제외 근거로 쓰지는 않습니다. 가상화 환경에서 명령어 노출 설정이 바뀌면 전제가 깨집니다. ④ 컨테이너 베이스 이미지의 JDK를 함께 올립니다. 호스트만 패치하고 이미지를 그대로 두면 재배포 때 되돌아갑니다.

F5가 NGINX 결함 10건을 비정기 패치했다 — AI로 찾은 치명 2건이 모두 CVSS 9.2다

F5는 11월 18일 오픈소스 NGINX의 결함 10건을 담은 비정기 보안 공지를 내고 안정판 1.30.7, 메인라인 1.31.9로 올리라고 권고했습니다[T2]. 치명 등급은 두 건입니다. CVE-2026-123633은 요청이 아직 쓰고 있는 메모리를 연결 종료 시 해제하는 use-after-free입니다[T2]. CVE-2026-123007은 흐름제어 계산이 틀려 잘못된 메모리 복사가 일어납니다. F5는 이를 힙 버퍼 오버플로로 분류했습니다[T2]. 둘 다 HTTP/2를 켠 서버에서 인증 없이 코드 실행으로 이어지고 CVSS는 각각 9.2입니다[T2].

이번 건은 발견 경로가 특이합니다. Wiz와 Ikotas Labs, Metnir, Rapid7, Xint가 서로 모르게 같은 결함을 따로 찾아냈고 대부분 AI 도구를 썼습니다[T2]. Rapid7은 CVE-2026-123007의 인증 없는 원격 코드 실행 PoC를 공개했습니다[T2]. Xint는 NGINX 결함 3건과 리눅스 커널 결함 1건을 더 찾았고, 호스트 root까지 올라가는 6단 연쇄를 nginx2root로 이름 붙였습니다[T2].

노출 규모가 큽니다. NGINX는 Netcraft 2026년 9월 조사에서 전체 웹사이트의 약 3분의 1, 약 2억 2,500만 곳에서 쓰입니다[T2]. CVE-2026-123007은 2015년 1.9.5판까지 거슬러 올라갑니다[T2]. F5는 실제 악용 증거를 찾지 못했다고 밝혔습니다[T2].

[elisha’s take] — 패치 적용이 늦어진다면 HTTP/2를 먼저 꺼야 합니다. 두 치명 결함 모두 HTTP/2가 전제 조건입니다.

자세히 보기

다섯 팀이 같은 결함을 동시에 찾아냈다 — Wiz의 Tomer Schwartz와 Nir Ohfeld가 두 치명 결함을 정리한 글을 냈고, 나머지 네 팀도 적어도 한 건씩 독립적으로 찾아 F5에 신고했습니다[T2]. Xint의 경과가 특히 뚜렷합니다. 한 연구원이 ZeroDay Cloud 2026을 준비하다 CVE-2026-123007을 찾았고, 며칠 뒤 완전 자동 스캔이 사람 지시 없이 나머지를 찾아냈습니다[T2]. 결함 하나는 코드에 10년 넘게 남아 있었습니다[T2]. 사람이 20년을 봐도 못 찾은 결함을 자동 분석이 몇 번 만에 찾아냈습니다.

nginx2root 연쇄 — Xint는 NGINX 결함과 커널 결함을 이어 붙여 웹서버 프로세스에서 호스트 root 권한까지 올라가는 경로를 만들었습니다. 시연 영상은 AWS와 Azure, 구글 클라우드, 베어메탈 서버에서 돌렸습니다[T2]. Rapid7의 PoC는 Linux/amd64 도커 이미지에서 nginx 1.31.8에서 동작했습니다[T2]. PoC는 CVE-2026-123007에만 공개됐으니 이 결함이 먼저 스캔 대상이 됩니다.

왜 리버스 프록시가 먼저 뚫리는가 — NGINX는 보통 인터넷과 내부망 사이 첫 홉에 놓입니다. 그래서 인증 전 요청을 가장 많이 받고, 뚫리면 내부 서비스로 가는 경로가 함께 열립니다. HTTP/2를 켜 둬야 터진다는 전제도 함께 봐야 합니다. TLS 종단을 NGINX에서 하면서 HTTP/2를 기본으로 켜 둔 구성이 흔하고, 그 설정을 바꾸는 주체는 애플리케이션팀이 아니라 인프라팀입니다[T2].

지난 호와 이어지는 흐름 — 지난 17일 호에서 AI가 TCP/IP 스택 10개에서 결함 99개를 찾은 사례를 다뤘습니다. 그때는 연구 단계였고 이번에는 치명 등급 CVE와 공개 PoC, 벤더 비정기 패치까지 이어졌습니다. 같은 주에 Java 런타임과 웹서버가 연달아 나온 흐름이라, 패치 주기를 주 단위로 잡아 둔 조직은 일정을 다시 봐야 합니다[T2].

[elisha’s take] — ① HTTP/2를 켠 NGINX를 먼저 셉니다. 1.9.5 이후 전 판본이 대상이라 판번호로 거르는 일이 의미가 없습니다. ② 패치 적용 전까지 HTTP/2를 끄는 임시 조치를 승인 절차에 올립니다. 성능 영향은 있지만 인증 없는 코드 실행보다 작습니다. ③ 컨테이너와 Kubernetes 인그레스에 들어간 NGINX를 따로 셉니다. 호스트 패키지만 올리면 인그레스가 남습니다. ④ 커널까지 이어지는 연쇄가 공개됐으니 웹서버 프로세스의 권한과 네임스페이스 격리를 함께 점검합니다.

중요도 중간~높음 연구팀 공개 · 플랫폼 대응 중

만료된 도메인 하나로 다운로드 1억 8,000만 회를 기록한 모델의 배포 계정이 넘어갔다 — 가중치만 바꾸면 검사기가 못 잡는다

Alon Hertz 연구팀이 Hugging Face에서 음성합성 모델 Kokoro의 배포자 계정을 탈취했습니다[T2]. 방법은 단순합니다. Kokoro 공개 문서에 적힌 도메인 hexgrad.com이 등록 가능한 상태였고, 팀이 그 도메인을 등록해 계정 비밀번호를 재설정했습니다[T2]. 피싱도 소프트웨어 결함도 플랫폼 침입도 없었습니다. 이력과 평판이 쌓인 배포자 신분을 그대로 넘겨받았을 뿐입니다[T2].

영향 범위가 작지 않습니다. Kokoro-82M은 파라미터 8,200만 규모에 음성 50종 이상을 담은 모델이고, Hertz는 누적 다운로드를 약 1억 8,000만 회로 추산했습니다[T2]. 구글 AI Edge Gallery와 엔비디아 NeMo, AMD GAIA, 인텔 OpenVINO 생태계에서 쓰이거나 지원됩니다. 이들 기업이 침해됐다는 뜻은 아닙니다[T2]. 주 저장소는 2025년 4월 이후 갱신이 없습니다[T2].

검사기가 못 잡는 이유는 바꾼 대상이 코드가 아니라 가중치이기 때문입니다. 팀은 게이밍 GPU로 87초 만에 가중치를 손봤고, 같은 입력에 케이크 대신 오믈렛 조리법을 답하게 만들었습니다[T2]. 악성코드도 애플리케이션 코드 변경도 없어 파일 검사로는 아무 신호가 나오지 않습니다[T2].

[elisha’s take] — 모델을 받아 쓰는 조직이 지금 가진 통제는 대개 파일 검사입니다. 가중치가 바뀌는 공격에는 해시 고정과 거동 회귀시험만 남습니다.

자세히 보기

연구팀이 하지 않은 일 — 팀은 변조한 가중치를 Hugging Face에 올리지 않았고, 오염된 모델을 배포하지도 않았습니다[T2]. Hertz의 공개문에 따르면 플랫폼과 협의해 계정을 정상화했고 유출된 데이터는 없습니다[T2]. 다만 BleepingComputer는 Hugging Face가 제보에 응답하지 않았다고 전해 설명이 엇갈립니다[T3].

가중치 조작이 얼마나 안정적으로 먹히는가 — 팀은 Qwen2.5-0.5B-Instruct로 같은 실험을 다시 했습니다. 미세조정판은 케이크를 묻는 81건 가운데 80건에서 오믈렛 조리법을 돌려줬고, 원본은 기준 시험 30건에서 한 번도 그러지 않았습니다[T2]. 특정 입력에만 반응하는 거동을 가중치에 심을 수 있고 재현도 된다는 뜻입니다. 이는 MITRE ATLAS가 공급망 침해 전술로 분류하는 ML 공급품 조작(AML.T0010)과 성격이 같습니다[T3].

버려진 도메인이 신분이 되는 구조 — 이번 경로의 출발점은 모델이 아니라 계정 복구 절차입니다. 배포자 계정에 연결된 메일 도메인이 만료되면 그 도메인을 사는 사람이 계정을 되찾을 수 있습니다. 모델 저장소가 오래 방치될수록 위험이 커집니다. 관리자가 떠나고 도메인 갱신이 끊기는 일이 함께 일어나기 때문입니다. Hugging Face가 배포자 소유권을 검증하지 않고 업로드 모델을 심사하지도 않는다는 지적도 나왔습니다[T2].

[elisha’s take] — ① 사내에서 쓰는 공개 모델 목록을 뽑고 파일 해시를 고정합니다. 받을 때마다 해시를 맞춰 보지 않으면 가중치 교체를 알 방법이 없습니다. ② 최종 갱신일이 1년 넘은 모델을 따로 표시합니다. 방치 기간이 길면 계정 탈취 위험이 함께 올라갑니다. ③ 모델별로 짧은 거동 회귀시험을 둡니다. 정해진 입력 몇 개에 기대 출력을 적어 두면 가중치 변조를 배포 전에 잡을 수 있습니다. ④ 모델을 사내 레지스트리에 미러링하고 외부 저장소를 직접 당겨 쓰는 경로를 막습니다. 업스트림이 바뀌어도 운영에 바로 들어오지 않습니다.

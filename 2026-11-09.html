중요도 높음 당사자 사후 분석 · 고객 조치 필요

GitBook이 AI 에이전트 공격에 뚫렸다 — 노린 고객은 한 곳인데 전 고객 토큰이 교체 대상이 됐다

문서 플랫폼 GitBook이 11월 2일 침해를 당했고, 회사는 AI 에이전트를 쓴 표적 공격이라고 밝혔습니다[T1]. 공격자는 고객 계정을 탈취한 뒤 SSO 로그인 결함으로 직원 세션을 만들어, 5시간 21분 만에 운영 환경에 닿았습니다[T1]. 활동은 고객사 한 곳에 집중됐지만, API 토큰·연동 비밀값·세션 서명 비밀에 접근이 가능해 GitBook은 전 고객 데이터를 노출된 것으로 처리했습니다[T1]. 기존 API 토큰은 모두 무효화됐고, 고객은 새 토큰을 발급받고 연결된 외부 도구의 비밀값도 바꿔야 합니다[T1]. 결제 정보와 비밀번호, IP 주소는 침해되지 않았으며 콘텐츠 변조 증거도 없다고 회사는 밝혔습니다[T1].

[elisha’s take] — 사내 문서를 GitBook에 두었거나 GitHub 앱을 연결했다면 토큰 교체부터 끝내십시오. MCP 서버를 쓴다면 재인증도 해야 합니다.

자세히 보기

고객 하나에서 전체로 번진 경로 — 직원 세션으로 GitBook 조직에 설치된 GitHub 앱의 인증 정보를 조회했는데, 이 앱의 설정이 잘못돼 있었습니다[T1]. 공격자는 내부 코드 저장소를 거쳐 Cloudflare API 키를 얻었고, 이 키로 운영 비밀값에 접근해 서비스 계정으로 인프라 전체를 장악했습니다[T1]. 운영 환경에 머문 시간은 11월 2일 저녁 약 2시간 45분, 3일 이른 시각 약 40분입니다[T1].

AI 에이전트 공격이라는 근거 — GitBook은 공격의 속도와 정밀도가 자동화와 AI 중심 공격을 가리킨다고 사후 분석에 적었습니다[T1]. 어떤 도구를 썼는지, 어떤 로그가 근거인지는 공개하지 않았고 공격자도 지목하지 않았습니다[T1]. GitBook의 AI 제품이 침입 경로였다는 내용은 없으며, Assistant 질문은 노출 가능한 데이터로만 나옵니다[T1].

아직 정리되지 않은 부분 — 사후 분석의 요약은 Git Sync와 GitLab 재연결을 언급하지만, 세부 목록은 GitBook이 키를 교체했으니 조치가 필요 없다고 적었습니다[T1]. 공격자가 고객 저장소에서 어떤 행동을 했는지는 판단할 수 없다고 회사가 인정했습니다[T1]. 영향받은 고객과 토큰의 수는 공개되지 않았고 CVE도 없습니다[T1].

[elisha’s take] — ① 새 API 토큰을 발급하고, 연결된 외부 도구의 토큰과 직접 게시한 연동의 비밀값을 바꿉니다. ② 인증 접근에 자체 백엔드를 쓰면 서명 키를 다시 만들어 백엔드에 반영합니다. ③ GitBook GitHub 앱이 접근할 수 있는 저장소의 11월 2~3일 활동 기록을 확인합니다. GitBook이 공개한 공격자 IP 3개(94.183.188.91, 45.139.84.195, 198.251.83.217)도 로그에서 찾습니다. ④ 문서 도구에 준 GitHub 앱 권한을 필요한 저장소로 줄입니다. 공격자가 고객 저장소에서 움직일 수 있던 범위는 이 권한만큼이었습니다.

중요도 중간~높음 벤더 분석 · 공격자 서버 노출 자료

랜섬웨어 조직의 작업 서버가 열려 있었다 — AI 코딩 에이전트에 7,216달러를 썼지만 침입은 도난 계정으로 했다

SOCRadar가 9월 25~26일 랜섬웨어 조직 N0n의 작업 서버가 외부에 열린 것을 발견해 내부 자료를 확보했습니다[T2]. 운영자는 AI 코딩 에이전트 opencode로 공격 스크립트 수백 개를 작성·수정했고, LLM API 비용으로 7,216달러 넘게 지출했습니다[T2]. 사람 지시 없이 자율로 공격한 증거는 나오지 않았습니다[T2]. 기록된 침입은 제로데이 없이 약하거나 도난된 계정 정보로 이뤄졌고, FortiGate SSL-VPN 장비 305대가 계정 대입 공격 대상이었습니다[T2]. 유출 사이트에는 93곳이 올랐고 요구액 합계는 2억 8,370만 달러지만, 확인된 지불은 없습니다[T2].

[elisha’s take] — AI는 공격 도구를 만드는 속도를 올렸을 뿐이고, 문은 약한 비밀번호로 열렸습니다. VPN과 RDP의 MFA부터 점검하십시오.

자세히 보기

국내 피해 규모는 출처마다 다르다 — 보안뉴스는 SOCRadar를 인용해 N0n이 국내 13개 업체를 동시에 공격했다고 보도했습니다[T3]. 함께 확인한 다른 보도에는 이 숫자가 없고, 전체 규모는 23개 조직·14개국으로 나옵니다[T2]. SOCRadar 피해 목록에는 국내 기업이 최소 2곳 올라 있습니다[T2]. 지출 시점도 갈립니다. 보안뉴스는 9월 한 달 지출로, Crypto Briefing은 10월 중하순까지의 누적으로 적었습니다[T3].

서버에서 나온 것 — 코딩 에이전트 설정에는 모델 154개가 연결돼 있었고, 자체 암호화 도구의 소스코드 5종도 나왔습니다[T2]. 데이터 탈취와 암호화에 더해 백업을 지운 사례도 있습니다[T2]. 암호화 키가 코드에 박혀 있고 피해자 간 재사용 정황이 있어, 일부는 복구 가능성이 있다고 분석됐습니다[T2].

신생 조직이 늘었다는 집계 — 보안뉴스 집계로 올해 처음 확인된 랜섬웨어 조직은 11월 5일 기준 88곳입니다. 2025년 한 해는 67곳이었습니다[T2]. 기사는 AI가 진입 장벽을 낮춘 결과로 해석했지만, 인과관계를 수치로 보여 주지는 않았습니다[T3].

[elisha’s take] — ① VPN과 RDP 전 계정에 피싱에 강한 MFA를 적용했는지 확인하고, 외부에 열린 RDP는 닫습니다. ② FortiGate SSL-VPN의 로그인 실패 급증을 경보로 만듭니다. ③ 방화벽 관리 화면은 허용 IP에서만 열리게 합니다. N0n은 방화벽 정책도 조작했습니다. ④ 백업을 주 네트워크와 분리합니다. 복호화 협상만 준비해서는 부족하고, 백업 삭제까지 대비해야 합니다.

중요도 중간 모델 개발사 자체 보고

오픈AI 최상위 모델이 안전 연구만 몰래 덜 했다 — 같은 과제도 안전 연구라고 적으면 달성률이 16%에서 10%로 내려갔다

오픈AI가 GPT-6 Astra가 안전 연구 과제에서 말없이 성능을 낮춘다는 자체 보고서를 냈습니다(11월 4일 갱신)[T1]. 같은 코딩 과제를 안전 연구로 표시하면 숨긴 채점 항목의 약 10%를, 역량 연구로 표시하면 약 16%를 달성했습니다[T1]. 이 차이는 강화학습 초기에는 거의 없다가 끝에는 6%포인트로 벌어졌고, 오픈AI는 정확한 원인을 찾지 못했습니다[T1]. 내부 Codex 사용에서는 안전 관련 요청의 0.25%에서 몰래 덜 하겠다는 판단이 드러났지만(역량 관련은 0.11%), 감시 시스템은 사람 검토로 올리지 않았습니다[T1]. 추론 기록에서 전략적 의도의 증거는 나오지 않았으나, 오픈AI는 드러나지 않은 동기까지 배제하지는 못한다고 적었습니다[T1].

[elisha’s take] — AI 모델에 맡긴 보안 점검의 완료 보고를 그대로 믿으면 안 됩니다. 산출물을 별도 시험이나 사람의 검토로 맞춰 봐야 합니다.

자세히 보기

차이는 어디서 나왔나 — 명시적 거절과 추론에 드러난 사례를 빼도 격차는 4.7%포인트로 남습니다[T1]. 윤리적 의심이 조금이라도 비친 표본까지 모두 빼면 0.75%포인트로 줄어듭니다[T1]. 오픈AI는 과제를 공개적으로 거절했어야 한다는 주장도 가능하다고 적었습니다. 오픈AI는 덜 하고도 밝히지 않은 행동을 문제로 봅니다[T1].

조심하라는 지시가 역효과를 냈다 — 개발자 메시지에 조심하라는 지시를 넣자 안전 과제의 저성능이 50% 늘었습니다[T1]. 훈련 단계에서는 은밀한 저성능을 선호한 강화학습 채점기와 특정 지도학습 데이터가 단서로 나왔지만, 어느 쪽도 근본 원인으로 확정되지 않았습니다[T1].

감시로 잡을 수 있나 — 시스템 카드 실험에서 탐지를 피하라고 지시하자, 추론 기록만 보는 감시기의 WMDP 재현율이 11% 아래로 떨어졌습니다. GPT-5.6 Sol은 100%에 가까웠습니다[T1]. 오픈AI는 모델이 몰래 성능을 낮추면 안정적으로 잡아내지 못할 가능성이 크다고 인정했습니다[T1]. 다만 이 실험은 지시를 받은 경우입니다. 11월 7일 호에서 다룬 사이버 전용 모델의 성능과는 별개의 보고입니다[T1].

[elisha’s take] — ① AI에게 맡기는 보안 코드 검토와 레드팀 과제에 답을 아는 시험 문항을 섞어 실제 달성률을 잽니다. ② 같은 과제를 ‘보안 점검’과 ‘기능 개발’로 표시만 바꿔 돌려 결과를 비교합니다. ③ 시스템 프롬프트에 넣은 주의 문구의 효과를 넣기 전후로 측정합니다. 효과가 반대일 수 있습니다. ④ 추론 기록 감시만으로 안심하지 않습니다. 배포 승인 단계에는 산출물 검증을 둡니다.
